# 如何放心地让 Agent 开展工作

> 一篇关于 Agent 可委托性的认知对齐材料。它不提供安慰，只提供判据。

---

## 一、先立对问题

过去两年，几乎每家公司都在做 Agent。做客服的、做代码审查的、做数据分析的、做招投标的——Demo 一个比一个漂亮。但走到一线问一句："有多少任务，你是真正交出去、不盯过程的？"答案寥寥。更常见的景象是：**Agent 做了一遍，人还要再做一遍。** Agent 写的报告，人逐句核；Agent 改的数据，人逐条对。复核一份 Agent 的产出，和自己动手做这件事，花的时间差不多。组织为 Agent 付出的成本一分没少，人的工作量也一分没省，唯一的增量是一层新增的人肉复核工序环节。

这就是本文的冲突：Agent 的数量在涨，被真正委托出去的任务却没有。需要公允地补一句：委托并非完全没有发生——Anthropic 基于真实对话的统计里，约 43% 的 AI 使用已经呈现自动化形态（后文详述）。但只要复核成本降不下来，"委托发生了"就名不副实：名义上交出去了，实际上还拴在人的注意力上。

流行的解释是"模型还不够强，等下一代"。这个解释听起来顺，但它把问题引向了等待——而且每一代新模型到来时，这套说辞都可以原样再说一遍。本文从一个更冷的问题出发：

> **什么条件下，把结果责任交给 Agent 而不盯过程，是理性的？**

先钉死一个词。标题里的"放心"，在本文中指的不是安全感，而是**有依据的信任**（warranted trust）。这个区别不是修辞。信任研究早就发现，人对自动化系统的信任感觉会系统性地失准——人对经常出错的系统过度放心，对相当可靠的系统疑神疑鬼。Lee 和 See 在 2004 年发表于 Human Factors 的经典综述里把问题的正确提法定了下来：目标不是"更多信任"，而是**"适当依赖"**（appropriate reliance）——信任要和系统的实际能力对得上（他们称之为校准，calibration）。对 Agent 过度信任，人会漏检错误；信任不足，人会全量复核——两种失准都破坏委托的经济性，方向相反，代价相同（Lee & See, [Trust in Automation, 2004](https://doi.org/10.1518/hfes.46.1.50_30392)）。二十多年后的证据更不乐观：一篇 CHI 2026 的综述系统梳理了人机决策研究，确认即便把 AI 的置信度直接展示给人看，人的依赖行为依然普遍校准不良（[CHI 2026 综述](https://dl.acm.org/doi/10.1145/3772318.3791467)）。

所以"如何放心"如果理解成"如何让人产生放心的感觉"，那是一条通往灾难的路——坏系统最擅长制造安全感。本文要问的是：放心的**依据**从哪来。

"再做一遍"不是执行不力的偶然，它有三个结构性来源，先在这里立个路标。其一，**错误不可见**：LLM 的输出流畅、自信，幻觉和静默偏离混在正确内容里，复核者只能逐字验证——这是"复核成本约等于重做成本"的直接来源。其二，**信任未被校准**：上面已经说过，该信多少这件事，人的感觉系统靠不住。其三，**Agent 无法可靠地"知道自己不知道"**：OpenAI 的 Agent 构建指南把"识别失败并优雅地把控制权交还给人"列为 Agent 的核心特征之一（[A Practical Guide to Building Agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)）——这句建议反过来承认：当前的 Agent 不能靠自己的判断发现失败，需要外部的失败检测机制来兜底。本文余下部分，就是把这三个来源逐一拆开、定价，并给出对应的机制。路线图：第二节把"委托"这件事本身拆成四个条件，第三节看清哪些约束撞不动，第四节把每条约束翻转成可投资的机会，第五节排布动手顺序和单任务判断，第六节画出机制再强也越不过去的边界，第七节收回答案。

## 二、拆解：委托为什么是四件事

"把一件事交出去"这个动作，经济学已经研究了五十年。委托代理理论（Principal-Agent Theory，Jensen & Meckling 1976）最初是为研究公司内部的委托关系而建——股东把经营权交给经理人，雇主把任务交给雇员——它的核心发现是：只要代理人与委托人的利益、信息不一致，委托就有缝隙，监督、激励、担保这一整套机制都是为弥合缝隙而生的。委托和"使用工具"的根本区别在于交出过程——一篇研究人机委托的论文说得很直白："如果你在委托时必须指定每一步细节，那你还不如自己做。委托是关于 relinquishing control——交出对整个过程的管理"（[A Framework for Studying AI Agent Behavior, arXiv:2509.25609](https://arxiv.org/html/2509.25609v2)）。

拿这套理论来照 Agent，不是因为 Agent 是"另一种员工"，而是因为它提供了一张被充分研究过的检查清单：委托成立需要什么，一项一项对照，缺什么就补什么。Agent 和人不一样——它没有私利、没有疲惫、没有情绪——所以每个条件在它身上呈现的形态都很不一样：有的变容易了，有的变难了，有的从原理上消失了。拆开看，委托成立需要四个条件。

**条件一：目标一致。** 人类员工和你的利益并不天然一致，所以才有薪酬、晋升、声誉这一整套激励机制去对齐。Agent 没有私利——从这个角度看它完美忠诚，不存在"谋私"的问题。但代价是：激励机制这条通道对它完全失效，剩下的唯一通道是**说清楚**——它只会做你说的，不会做你想的。而"把想说的说清楚"这件事，远比看上去难——难在两层：一层是你以为自己说清了，其实没有，意图的大部分沉在水面之下；另一层是你真写下来的那部分，也处处是歧义的藏身之所。第三节第一站会把它讲透。

**条件二：行为可观察。** 表面上看，Agent 比人类员工透明得多：每一步推理、每一次工具调用都有完整日志，人类员工的脑子你可看不见。但这里有一个悖论：**我们拥有空前的过程数据，却没有更多的理解。** 看一个员工做事，你能从共同的业务上下文推断他"懂了没有"；看 Agent 的完整轨迹，你依然不知道它哪一步理解偏了——日志告诉你它调了哪个接口、返回了什么，但不告诉你它把"尽快发货"理解成了"跳过缺货检查"。数据不等于可观察性。于是可观察性的重心被挤到了最后一道闸上：结果验证。

**条件三：监督与问责。** 这两个词常被混用，但必须切开，因为它们的命运完全不同。监督——日志、抽检、评测——是可以工程化的，第四节的五个机会里有两个半在干这件事；问责——做砸了承担后果——永远无法对 Agent 成立。Agent 不能赔钱、不能被解雇、不在乎声誉，它这次搞砸和下次搞砸，对它没有任何区别。问责本质上需要一个能感受后果的主体，而 Agent 不是。监督可以补，问责补不了。

**条件四：风险可兜底。** 委托人敢放手，前提是最坏情况接得住。兜底不是态度问题，是算术：失败率乘上失败损失，必须小于委托省下的钱（第五节给出完整公式）。如果一次失败的损失无界，再高的成功率也换不来委托。

四个条件摆完，对照 Agent 的现状：条件一切了条窄通道，条件二有个悖论，条件三缺了一半，条件四靠人为设计。**缺口的总和，就是"人还要再做一遍"的全部内容**——现在的人不是流程里的"复核者"，而是所有缺失机制的肉身替代品：人肉验证器、人肉问责制、人肉信任校准器。这三样肉身替代品有一个共同点：都按次计费，都不产生积累。

有人会反驳：这不就是磨合期吗？带新员工也要带半年，复核几个月，他就会了。

这个反驳必须正面接住，因为它有一半是对的：补位本身不是错，带新员工确实要补位。真正的区别在于**沉淀**。带人时，补位会沉淀——员工在成长，你复核的频率自然下降，半年后他可以独当一面。带 Agent 时，如果你在复核中磨出的那些判断——"这种数据要这么核""那种表述一看就有问题"——没有变成测试集、验收标准、示例库这些**资产**，那么补位就永远不会减少。半年后再看，你还在逐句核。**你不是在带徒弟，是在当永动机。** 问题从来不是补位，而是补位没有沉淀。

## 三、五条硬约束

补位为什么没有沉淀？多数团队给出的答案是把希望押给时间——"等下一代模型来，这些缺口自然就消了"。这个押注对不对，不能靠感觉回答。得先看清：这些缺口里，哪些是技术进步确实填得平的，哪些是规则本身、撞上去纹丝不动的。

本文称后者为**硬约束**：技术进步消不掉、只能管理或定价的约束。辨认它们的最好方法，是跟着一个委托任务走一遍它的一生——从被交代，到被执行，到被拉长，到被检查，到被再次委托。

### 第一站：任务被交代——意图无法完整传递

委托的第一步是把任务说清楚。而这里压着一条哲学上早有定论的硬约束：**我们知道的多于我们能言说的**（Polanyi 悖论）。

这句话出自科学哲学家 Michael Polanyi，原文是 "We can know more than we can tell." 他由此提出默会知识（tacit knowledge）的概念：大量真正管用的知识，是以经验、品味、直觉的形式存在的，知道的人自己也无法把它完整说出来——会骑车的人讲不清自己如何保持平衡，老编辑扫一眼标题就知道不行，但写不出一条可执行的判定规则。

一个业务任务的真实意图，大部分是这种默会知识：什么算"好"、什么情况算"异常"、哪些约束是死的哪些可以通融、客户上次为什么发火。这些东西在委托人的脑子里，能写进 prompt 和政策文档的只是冰山一角。人类员工可以用数年共事去浸泡这些默会知识，Agent 只能靠你写给它的东西——写得含糊的地方，它不会来问你，只会替你掷硬币。这条约束卡的不是错误、不是验证、不是链条、不是速度，而是委托的起点本身：任务能否被完整给定。这一关不过，后面四条约束都轮不到谈。

这条约束有一个非常硬核的实验证据，来自对 τ-bench 的日志分析。τ-bench 是 Sierra 的研究者设计的 Agent 评测（[arXiv:2406.12045](https://arxiv.org/abs/2406.12045)），模拟零售和航空两个真实业务领域的客服场景：Agent 要在多轮对话中理解用户诉求、调用 API、并且严格遵守一份书面政策文档，最后以数据库的终态来判分。这套设计与企业的内部署几乎同构——你的客服 Agent 面对的同样是"用户诉求 + 业务系统接口 + 内部政策文档"这三件套。一篇专门检查其运行日志的研究（[arXiv:2605.08545](https://arxiv.org/pdf/2605.08545)）发现：把定义有误或含歧义的任务剔除之后，Agent 的平均 pass^5（同一任务独立跑 5 次、每次都成功的概率）从 20.8% 升到约 40%，**大致翻倍**。换句话说，相当一部分被记在"Agent 不可靠"账上的失败，真正的责任人是**任务定义不清**——政策文档的歧义、验收标准的缺失。以为是模型问题，其实是管理问题。这个发现对企业管理者极其重要：连公开发表的 benchmark 都藏着这么多歧义任务，你内部那份没人消过歧的政策文档，歧义只会更多。

它杀死的信念是："把文档丢给知识库，AI 就懂我们业务了。"

### 第二站：任务被执行——错误不可消除

任务交代完了，Agent 开始干活。第二条硬约束在这里：**开放任务上，错误不可消除，只能被管理和定价。**

大语言模型的输出本质上是概率分布上的采样——每次生成，都是在所有可能续写里按概率掷一次骰子。"错"不是 bug，而是方差——bug 可以修完，方差只能收窄不能删除。想把错误率真正压到零，只有一个办法：把任务收窄到封闭域，即答案确定、可完全枚举的那类问题——棋类、数值计算、有标准答案的客观题都在此列，而绝大多数"写一份""做一笔"的真实业务不在。也就是说，**可靠性只能用任务范围来换**。

这条约束最量化的证据来自 METR——一家专门测量前沿 AI 能力的研究机构——对 2019–2025 年前沿模型的测量（[arXiv:2503.14499](https://arxiv.org/abs/2503.14499)）。它的方法值得一提：不直接用 benchmark 分数说事，而是用"人类完成这个任务需要多长时间"来标定任务难度，再拟合模型成功率随任务长度变化的曲线（logistic 曲线，一条 S 形曲线：短任务上成功率贴着 100%，过了某个长度之后陡然下坠），报告"x% 成功率对应的任务时长"（他们称之为时间跨度，time horizon）。这个方法的妙处在于，它把"AI 有多强"这个说不清的问题，翻译成了"AI 能可靠接手多长的活"这个可以对照自己业务的问题。核心数字有四组：

- 对"人类 4 分钟内能完成"的任务，当前最好的模型成功率接近 100%；
- 对"人类需要 4 小时以上"的任务，成功率**低于 10%**；
- 以 50% 成功率定义的时间跨度，自 2019 年起以约**每 7 个月翻倍**的速度指数增长（稳健估计为每年翻倍 1–4 次，2024 年后可能还在加速；在 SWE-bench Verified——由人工逐条校验过的 500 个真实软件修复任务——这个子集上，拟合出的翻倍速度甚至快于 3 个月）；
- 但论文同时强调：80%、95% 这类高置信度阈值下的时间跨度，**远短于** 50% 那条曲线。

最后一组数字是委托问题的心脏。用论文自己的话说：最好的模型**偶尔**能完成需要专家数小时的任务，但**只能可靠地完成**几分钟量级的任务。"偶尔能"是运气分布的尾巴，"可靠地能"是曲线的躯干；能力涨了六七年，两者之间的鸿沟没有闭合，只是整体上移。翻译成委托语言：当前可委托的任务边界，大致就在人类几分钟到十几分钟的任务之间；想委托更长的任务，成功率会跌破经济上可接受的阈值。这个方法可以直接为你所用：给候选委托任务估一个"人类时长"，再对照当前模型的时间跨度曲线粗判可行性——只是要看 80%、95% 那些高置信度曲线，别看 50% 那条。

注意，委托恰恰买在"可靠地能"上。你委托一件事，是因为相信它**每次**都会被做对，而不是有相当概率被做对。这条约束杀死的信念是："等模型足够好，就不需要流程和护栏了。"

### 第三站：任务被拉长——可靠性是乘法

单个步骤做得不错，那把二十步串起来呢？第三条硬约束是算术：**可靠性是乘法，不是加法。**

单步可靠性 95%，连续二十步，端到端成功率的上界是 0.95 的 20 次方——约 36%。就算把单步可靠性做到 99%，一百步之后也只剩约 37%。这个算术还解释了工程上一个反直觉的体验：链条从 10 步加长到 20 步，成功率不是减半，而是从约 60% 掉到约 36%——乘法的意思是，加倍的链条吃掉的是成功率的平方。这不是工程经验，是条件概率：链条要全对，每一步都得对，各步都对的概率就是逐个相乘。这个乘法模型有个前提——各步相互独立——先把前提摆出来，再看真实 Agent 偏在哪边。

真实 Agent 的情况在两个方向上偏离独立假设。一个修正项让它更糟：Agent 是有状态的，一步的错误会改变后续所有步骤的轨迹，错误之间正相关——Anthropic 在构建多 Agent 系统的复盘里说得直白，"Agent 是有状态的，错误会复利累积……传统软件里的小问题对 Agent 可能是灾难性的；一步失败会让 Agent 走向完全不同的方向"（[Anthropic Engineering](https://www.anthropic.com/engineering/built-multi-agent-research-system)）。Cognition（Devin 团队）复盘多 Agent 架构时观察到同类效应的另一种形态：子 Agent 只拿到任务片段，理解产生偏差；不同子 Agent 基于各自未声明的假设行动，产出互相矛盾——错误不仅沿链条传递，还会在分支之间互相污染（[Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)）。另一个修正项让局面略好：检查点、重试这类恢复机制能挽回一部分失败。两个修正项不改变主结论：链条越长，对单步可靠性的要求越苛刻，而单步可靠性被第二条硬约束压在 1 以下。

把第二、第三条放在一起，会推出一个可以在原理层面**定性预言**实验结果的结论：成功率必然随任务长度快速下跌。这正是 METR 实测到的那条曲线——看到它时你不该意外，它不是某种模型缺陷，是算术。这也解释了为什么"延长链条"比"提升单步智能"难得多：单步可靠性必须趋近 1，长任务才撑得起来，而趋近 1 恰恰是最贵的那段路。

这条约束杀死的信念是："这个 Agent 每步都做得挺好，串成完整流程应该没问题。"

### 第四站：结果被检查——验证与生成不对称

任务做完，轮到委托人检查。第四条硬约束在这里，它可能是五条里最反直觉的：**验证成本与生成成本不对称，且这个不对称随模型变强而加剧。**

生成是采样，验证是对照真值——这两件事的成本没有任何必然关系。解一道数独要很久，验证一个解只要一眼；反过来，核查一篇长文的每个事实，比写这篇长文还累——网上造谣和辟谣的成本差距有个专门的说法，Brandolini 定律：驳斥胡说八道所需的能量比制造它高一个数量级。OpenAI 研究员 Jason Wei 把这个现象总结为"验证不对称"（asymmetry of verification），并提出"验证者定律"（verifier's law）：一个任务越"可验证"，AI 解决它的速度上限就越高。他给出了可验证任务的五个性质：**客观真值**（有公认的对错）、**验证快速**（几秒钟判完）、**可规模化**（能自动批量判）、**低噪声**（判定结果稳定，不随判断者心情漂移）、**奖励连续**（能给出"离正确还有多远"的中间信号，而不只是全对或全错）（[verifier's law](https://www.jasonwei.net/blog/asymmetry-of-verification-and-verifiers-law)）。

拿这五条去量你手里的任务，比争论"AI 到底行不行"有用得多。代码几乎五条全占：编译器和测试给客观真值，跑一遍只要几秒，持续集成（CI）天然可规模化，结果稳定，报错日志提供连续信号——所以代码是 AI 进展最快的领域，不是巧合。而"写一份让管理层满意的经营分析"几乎一条不占：没有客观真值，判定靠品味，快不了，也规模化不了——所以它进展慢，同样不是巧合。一个可操作的做法：给每个候选任务估一个"验证成本 ÷ 求解成本"的比值，比值越低越适合委托；比值接近或超过 1 的，当前不宜全委托。还要注意这个比值的漂移方向：模型每迭代一代，求解端就更便宜一点，验证端原地不动——委托的经济账，会越来越多地由验证那一项说了算。

关键推论在"加剧"两个字上：模型变强，压低的只是生成端的成本，验证端分毫不动。生成越便宜，涌向验证端的工作量越大，验证就越成为瓶颈。**所以"模型变强"不仅不解决委托问题，反而让瓶颈更集中地暴露在验证上。** 真实世界的采用数据印证了这个推理。Anthropic 的 Economic Index 基于对约一百万条真实用户对话的分析（[来源](https://www.anthropic.com/news/the-anthropic-economic-index)），发现：当前 AI 使用中增强模式（augmentation，人机协作）占 57%，自动化模式（automation，AI 直接执行）占 43%；而使用最集中的是计算机/数学类任务，占全部查询量的 37.2%。本文认为，这不是因为模型最懂代码，而是因为**代码自带验证器**：编译器、测试、类型系统，都是现成的结果校验。市场已经在用脚投票：先被委托的，永远是验证便宜的任务。

这条约束杀死的信念是："Agent 产出越多，组织效率越高。"——超出验证吞吐的产出，不是资产，是负债。

### 第五站：关系在延续——信任攒得很慢

假设前四站都过了：任务定义清晰，错误率可接受，链条够短，验证也便宜。是不是就可以全面委托了？还有最后一条硬约束，它长在委托人这一侧：**委托关系的深化速度，受限于验证记录的积累速度；而验证记录的积累速度，受限于人的注意力与真值的可得性。**

信任不是能力的函数，是验证记录的函数。能力可以七个月翻一倍（METR 的时间跨度曲线），但人消化结果、积累证据的速度不变。委托关系的深化因此有一个绕不开的物理过程：一笔一笔地验证，一条一条地攒记录。这里的"记录"不是比喻：哪类任务、跑了多少次、成功率多少、失败长什么样、处置是否及时——它们合起来，才构成"敢不敢再交多一点"的依据。这个过程的快慢不取决于模型迭代多快，而取决于组织一天能消化多少验证结论——人的注意力和真值（判断对错所依据的标准答案）都是稀缺资源。而且第一节的校准研究在这里显出第二重含义：验证记录不仅攒得慢，还攒不准——人对系统的感觉会系统性偏离它的实际能力。信任这座蓄水池，进水慢，水表还不准。

更麻烦的是，人这一侧还会退化。1983 年，工业自动化方兴未艾、工厂里的自动控制系统正在批量取代操作工，心理学家 Lisanne Bainbridge 发表了经典论文《自动化的讽刺》（[Ironies of Automation](https://doi.org/10.1016/0005-1098(83)90046-8)），提出两个至今未被推翻的论点。第一：自动化并不把人移出系统，而是把人变成监控者——而"长时间盯着一个通常正确的系统，在罕见的异常时刻迅速反应"，恰恰是人类注意力机制最不擅长的事。第二：自动化程度越高，人亲自动手的机会越少，技能越萎缩；一旦系统失效需要接管，人反而更没有能力接管。合起来是一个悖论：越依赖自动化，越需要人的接管能力；越自动化，人越失去接管能力。四十年后，这篇工业自动化时代的论文读起来像在给 LLM 时代写预言。

这条约束解释了为什么"benchmark 分数到了，组织就会用起来"是错的：能力曲线和委托曲线之间，有一个由验证吞吐决定的、不可压缩的时间差。采纳必然滞后，而且应该滞后——没有验证记录支撑的提前信任，正是第一节说的"没有依据的放心"。反过来说，一个组织委托深度的上限，可以用它的验证吞吐直接估出来——这比盯着模型发布日历来规划 Agent 路线图，要靠谱得多。

## 四、五个机会

硬约束读下来容易丧气。现在换个方向——查理·芒格管这个叫逆向思维：不问"怎样让 Agent 可信"，反过来问"**是什么让我不敢委托**"。把每一条"不敢"列出来，逐条翻转，每一条都是可投资的工程方向。

五条硬约束，恰好对应五条"不敢"，也恰好对应五个机会：意图不可完整传递，翻出意图资产化；错误不可消除，翻出错误预算制；可靠性是乘法，翻出短链装门；验证与生成不对称，翻出验证前置；信任攒得慢，翻出授权阶梯。本节先把"有什么可建"摆全；先建哪个，是第五节的题目。

### 机会一：意图资产化

> "我不敢，因为它不懂我们的业务，做出来方向是偏的。"

既然意图不可完整传递，那就把"传递意图"本身当成工程对象，把传出去的那部分建成**资产**：可执行的验收标准、黄金示例库、被消过歧的政策文档。三件套各有分工：验收标准回答"什么样算做完做对"，最好可执行、能跑分；黄金示例库回答"照着这个样做"，正例反例都要覆盖；消过歧的政策文档回答"规则到底是什么意思"，把每一处"视情况而定"都逼成明确的分支。注意"资产"和"文档"的区别：文档写完放进 wiki 就死了，资产是持续维护的工程制品——每次复核发现 Agent 理解偏了，纠正的同时把这个判断沉淀成一条示例或一条验收标准，下一次复核就少一件事。于是复核这个动作的性质变了：它不再是纯消耗，而是带着副产品的生产——每复核一次，资产厚一分，复核成本就低一分。这就是"沉淀"的完整闭环，也是"带徒弟"和"永动机"在操作层面的全部差别。

这项资产的收益率不是拍脑袋，是实测过的：τ-bench 的日志分析（第三节第一站）给出的正是"消歧"这一项动作的收益——排除掉有歧义的任务定义后，Agent 重复运行的成功率大致翻倍（20.8% → 约 40%）。**先修任务定义，比先修 Agent 本身更值钱。**

### 机会二：错误预算制

> "我不敢，因为不知道它哪次会错。"

既然错误不可消除，那就放弃"零错误"的幻想，把错误从恐惧对象变成管理对象。这套纪律有一个成熟的现成版本：Google 的 SRE（网站可靠性工程）体系里的**错误预算**（error budget）。它值得展开讲，因为它的两层设计恰好对症。

第一层回答"为什么不追 100% 可靠"（[Google SRE Book, Embracing Risk](https://sre.google/sre-book/embracing-risk/)）。SRE 的经验是：可靠性每多一个"9"，成本可能上涨一个数量级，而用户根本分辨不出来——用户的体验被自己那台 99% 可靠的手机和网络主导，服务端做到 99.99% 还是 99.999%，他感知不到差别。追求极端可靠性，买到的只是开发速度的停滞。所以 SRE 给每个服务设一个"够用就好"的可靠性目标（SLO，比如"本季度 99.9% 的请求要成功"），目标既是下限也是上限——超出目标的可靠性是浪费。

第二层回答"预算怎么管住行为"。按季度把 SLO 和实际表现的差额算成"错误预算"：预算没花完，新版本随便推；预算耗尽，冻结发布，资源转投测试和稳定性还债，直到回到预算以内。妙处在于它把"要速度还是要稳定"的政治争吵变成了看数字说话——开发团队盯着余额自我约束，不需要别人拦。

移植到 Agent 上：建立失败模式分类学（它会以哪几种方式出错——调错接口、误解政策、超长跑偏，各自单列），每类错误有预算、有检测手段、有处置路径；预算内自主运行，预算外自动升级给人。注意它和机会五的分工：错误预算管"某一类错误还能容忍几次"，授权阶梯管"这个 Agent 整体被信任到哪一级"——前者按错误记账，后者按信任记账。

要坦白一句：这是五个机会里证据最弱的一个。它是从运维领域**类比移植**来的纪律，还没有人系统验证过"Agent 错误预算"在实践中的效果。但它的前提——错误不可消除——是五条硬约束里最硬的一条，所以方向不赌错。

### 机会三：短链装门

> "我不敢，因为它单步都挺好，一长就崩。"

既然 p 的 n 次方不可违抗，就不要跟它对抗，而是管理 n。两个动作：**切短**，把长任务分解成短链条；**装门**，在链条之间插入确定性的、程序化的检查点——通过闸门才进入下一段，通不过就停在原地。门必须是确定性的程序，而不是另一个 LLM 的"我觉得行"——否则门的可靠性本身又成了乘法里的一个新因子。配合检查点恢复（checkpoint/resume），出错从断点继续，而不是从头再来。Agent 的自主只发生在门与门之间的短区间里——**自主性不是被取消了，而是被装进了笼子里，笼子的大小由你定。**

工程界对"切短"有高度一致的体感。12-Factor Agents 的第十条就是"小而专注的 Agent"：上下文和步数膨胀之后，错误率会显著上升，社区称之为 dumb zone（[12-Factor Agents](https://github.com/humanlayer/12-factor-agents)）。Anthropic 的工程实践把"装门"做得更细（[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)；[多 Agent 系统复盘](https://www.anthropic.com/engineering/built-multi-agent-research-system)）：把任务切成固定子任务的 prompt chaining，在步骤之间加入程序化检查，用延迟换准确率；对会改动持久状态的 Agent 采用终态评测（end-state evaluation）——不逐步检查过程，只比对最终的数据库或世界状态对不对——并把复杂流程拆成离散检查点；工具失败时不藏着掖着，而是明确告知 Agent 让它自适应处理，按他们的说法"效果出乎意料地好"。还有一个容易被忽视的细节：他们用 Agent 自动测试并重写工具描述，仅此一项就使后续 Agent 的任务完成时间下降 40%——坏的工具描述会把 Agent 带上完全错误的路径。门要装，门上的标签也要写对。

### 机会四：验证前置

> "我不敢，因为确认它做对了，比我自己做还贵。"

验证成本是任务的属性，但可以被前置成**工程资产**——这是五个机会里杠杆率最高的一个，因为它是其他几个的前提：错误预算需要检测手段，授权阶梯需要信任证据，意图资产需要验收标准，全部来自验证器。

verifier's law 有一个常被执行者忽略的推论：验证不对称不是固定不变的，它可以被工程动作改善。提前写好的测试集、答案键、形式化约束，能把验证成本从"重做一遍"降到"跑一遍测试"。验证资产有两条腿。**第一条是结果验证**：测试集、答案键、终态校验（不看过程，只比对最终状态对不对——τ-bench 正是用"比对最终数据库状态"来判分的，上一节 Anthropic 的终态评测是同一思想）。**第二条是过程审计**：Agent 留下的完整执行轨迹——每一步推理、每一次工具调用——可回放、可审计、可评测。第二条腿常被忽视，但它是 Agent **独有**的资产：人类员工永远不可能给你这样的透明度。可观察性悖论说的是"数据不等于理解"，而工程化的回答是把数据变成审计能力。验证资产到位之后，复核的姿势也跟着变：从"逐字读产出"变成"看仪表盘、查告警"——人验的是验证器，不再是每一件产出。

建这份资产不需要等大工程，Anthropic 的评测驱动经验（[多 Agent 系统复盘](https://www.anthropic.com/engineering/built-multi-agent-research-system)）有三条可直接照抄：一是**立刻用小样本开始**——约 20 条真实查询，就足以在早期看到 30% → 80% 级别的效应量，不要等到能建几百条的大评测集再动手；二是用 LLM 做评判时，单一 prompt、0.0–1.0 打分加 pass/fail 的格式最稳定；三是**人工评测不可省**——自动评测漏掉的边界案例（比如 Agent 偏爱引用 SEO 内容农场而非权威 PDF），只有人工抽检抓得到。

验证器建起来之后，还可以反过来喂给生成端。Anthropic 称之为 evaluator-optimizer 模式：一个 LLM 生成，另一个按明确的验收标准评估并反馈，循环迭代直到达标（[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)）。它的适用前提恰好就是本节的前提——存在清晰的评估标准，且迭代能产生可度量的改进。

一份验证资产同时服务三层：开发期的评测、上线前的验收、运行时的护栏。一次投入，三次产出。它还有一个跨周期的属性：模型会换，供应商会换，但验收标准和测试集跟着业务走——验证资产是 Agent 项目里少数不随技术迭代贬值的投入。

### 机会五：授权阶梯

> "我不敢，因为一次事故，一年的信任就归零。"

既然信任只能由验证记录逐笔累积，那就把这个累积过程**制度化**——像带实习生一样带 Agent：只读观察 → 出建议 → 审批后执行 → 限定范围自主 → 扩大范围。每一级对应一种明确的残余风险：只读观察期，它犯错的最大代价是你读到一条错信息；出建议期，代价是你采纳了一条错建议；审批执行期，代价是审批人放了水。只有验证记录攒到足以证明某一级"稳"了，才放它爬下一级。每一级的晋升标准用指标说话，不用感觉说话——核心指标是 pass^k：同一任务独立运行 k 次、每次都成功的概率。它和单次成功率（pass^1）的区别必须掰开：单次成功是演示，次次成功才是委托。单次成功率掩盖方差，而真实业务要的是"每次都做对"。τ-bench 的实测给过清醒剂：即使最强的工具调用型（function-calling）Agent（gpt-4o），单次任务成功率也低于 50%；用 pass^k 衡量，同一任务独立跑 8 次全都成功的概率低于 25%（retail 域，[arXiv:2406.12045](https://arxiv.org/abs/2406.12045)）。pass^1 和 pass^8 之间的落差，就是"看起来行"和"敢委托"之间的距离。

pass^k 还有一层诊断用法：pass^1 高而 pass^k 低，说明输出方差大，这类任务必须配验证器兜底才谈得上委托；pass^1 本身就低的，先回到机会一——多半是任务定义出了问题。对要委托的任务类型做 k 次重复评测，是比任何 demo 都诚实的尽职调查。

阶梯的两个配套设计：一是**闸门**——高风险动作（支付、删除、对外发送）无论爬到哪一级都强制人工批准，OpenAI 的 Agent 实践指南把"超过失败阈值"（重试或动作次数触顶）和"高风险动作"列为两类必须的人工介入触发器，并指出人工介入机制本身就是"在不牺牲体验的前提下提升真实表现"的手段（[A Practical Guide to Building Agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)）；二是**演练**——保留人定期手动操作的习惯，否则按 Bainbridge 的警告，"human-in-the-loop"会退化成名义上在环、实际上接不住。演练的成本可以很低：每月留一天由人手工走一遍关键流程，或复盘时人工重做一次 Agent 的周期产出——买到的是接管能力的保鲜。

有实验证据支持这套设计：一项人机团队模拟实验显示，按置信度阈值做条件委托——AI 置信度高于阈值就自动采用，低于阈值就转人工——团队准确率（84.1%）超过了 AI 单独作战（77.7%），也超过人单独作战（[Confidence-Based Trust Calibration, 2025](https://thesai.org/Downloads/Volume16No12/Paper_122-Confidence_Based_Trust_Calibration_in_Human_AI_Teams.pdf)）。但要注意这个结论的前提：它要求 Agent 报告的置信度本身是准的，而当前 LLM 的置信度校准普遍不佳——说"我有九成把握"和真有九成正确率是两回事（相关综述见 [arXiv:2311.08298](https://arxiv.org/abs/2311.08298)）。置信度校准本身，是这套机制的地基之一。

五个机会摆完，回看第二节的四条件：意图资产化补上目标一致的窄通道，验证前置补上可观察性，错误预算制和短链装门补上监督那半个，授权阶梯补上风险兜底——**四个条件补上了三个半。剩下的半个，是第六节的事。**

## 五、做法：先做什么，怎么判断一个任务能不能委托

五个机会不是平均投资的。排序依据两套逻辑，分层使用：

**第一位不靠诊断，靠依赖。** 验证前置永远先动工——不是因为你的瓶颈恰好在那，而是因为它在结构上就是使能器：错误预算要靠它检测，授权阶梯要靠它供证据，意图资产里的验收标准本身就是验证器的一种。这不是经验判断，是结构判断。

**第二位起靠诊断。** 在意图资产、错误预算、短链装门之间，打你当前最紧的那个约束。简易诊断：任务总是跑偏——先建意图资产；流程一长就崩——先短链装门；出了错没人管、反复犯同类错——先立错误预算。

**授权阶梯贯穿始终。** 它不是一步投资，而是一种姿势：从第一天起，让 Agent 在最低一级（只读观察）真实运行，边跑边攒验证记录。等它"够格"再上线的思路是错的——资格只能在真实的、低权限的运行中挣出来。

落到单个任务上，能不能委托，四个问题，按顺序问：

| 问 | 答"否"怎么办 |
|---|---|
| ① 任务能被完整给定吗？——验收标准、示例写得出来吗？ | 先建意图资产，别急着上 Agent |
| ② 验证能前置吗？ | 定位增强模式（Agent 出草稿，人负责），不装委托 |
| ③ 一致性够吗、链条超半径吗？——pass^k 实测多少？ | 短链装门，缩小自主区间 |
| ④ 最坏损失接得住吗？ | 加闸门，压低授权阶梯级数 |

四问全过，才是委托候选。这个表值得你忘掉本文所有论证之后仍然带走。

四问的顺序不是随便排的，每一问都对应一条硬约束，且互为前提。①对应意图传递：答"否"说明任务还锁在委托人的默会知识里，此时上 Agent 等于让它猜谜。②对应验证不对称：验证贵过重做的任务，委托的经济性永远不成立，强上只会制造"AI 产出一堆、人复核一堆"的双倍工作量。③对应错误不可消除与乘法可靠性：pass^k 实测过低，说明方差太大或链条太长，问题在结构不在运气。④对应风险兜底：损失无界时，成功率再高也只是赌博的赔率好了一点。①②不过，③④无从谈起——说不清的任务没法谈可靠性，没法验证的可靠性没法谈授权。

第①问还有一个好用的筛选器。OpenAI 的实践指南给出过三条标准：优先选传统规则引擎做不好的流程——需要**复杂判断**的（如退款审批）、**规则集难维护**的（如供应商安全审查）、**重度依赖非结构化数据**的（如保险理赔）；三条都不满足的，确定性方案往往就够了，不必请 Agent 出山（[A Practical Guide to Building Agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)）。

至于经济账，一个任务值不值得委托，可以用一条公式记：委托收益 = 人亲自做的成本 −（Agent 执行成本 + 验证成本 + 失败率 × 失败损失），大于零才委托。它是第①②问的成本估算工具——仅此而已，本文不指望它解释更多（这条公式是本文对委托收益的综合表述，不是某篇论文的原式）。公式里的每一项都有出处：验证成本来自机会四建的资产，失败率来自 pass^k 的实测，失败损失来自第④问的兜底设计——它不是拍脑袋的算盘，是前几节机制的记账本。右半边还有两个更规范的度量可以借用：Stanford 提出的 cost-of-pass（[arXiv:2504.13359](https://arxiv.org/abs/2504.13359)），把"产出一个正确解的期望货币成本"作为准确率和推理成本的联合度量，其实就是公式里 Agent 侧成本的标准记法；Princeton 的 AI Agents That Matter（[arXiv:2407.01502](https://arxiv.org/abs/2407.01502)）则从评测角度给出配套纪律：评估 Agent 时必须同时报告成本与准确率——只看成功率，会系统性地高估一个 Agent 的可委托性。

把四问和公式合起来用，可以得到一条粗略的委托优先顺序（这是调研报告给出的综合判断）：有自动化测试覆盖的软件任务最先，其次是结构化数据处理和有终态校验的业务操作，再次是检索研究类任务（需配引用核查），创意和事实密集型写作排在最后——验证太贵，保持增强模式。部署节奏上，OpenAI 的建议与此同向：从小做起，用真实用户验证，随时间逐步扩展能力（"Start small, validate with real users, grow capabilities over time"）。

## 六、边界：三个"永远"

五个机会把委托代理的四个条件补上了三个半。现在说补不上的部分——这门课不是 Agent 布道文，它画的是委托的版图：哪里可以，以及**哪里永远不行**。五条硬约束推出三个"无论模型多强都不变"的边界。画边界不是泼冷水：知道哪里永远不行，"哪里可以"才从愿望变成版图。

**经济边界：验证约等于重做的任务，永远不委托。** 事实核查密集的长文、高度依赖品味的创意——这类任务里"确认它对了"和"自己做一遍"一样贵，委托的经济性永远不成立。用 verifier's law 的语言说，这类任务的"验证成本 ÷ 求解成本"比值恒大于 1——这不是模型暂时不够强，而是任务属性本身。对它们，诚实的定位是增强：Agent 出草稿、出线索、出初稿，人对结果负责。把增强包装成自动化，是当下 Agent 项目最常见的自欺。

**风险边界：不可逆、高损的动作，永远保留人工闸门。** 支付、删除、对外发送、修改生产数据——这些动作一旦发生无法撤回。授权阶梯可以一级级爬，但闸门不随级数取消。这不是阶段性的谨慎，是永久的架构。还要补一句 Bainbridge 式的提醒：闸门要有效，门后的人必须接得住——关键岗位要定期人工演练，否则闸门后站着的只是一个技能已经萎缩的名义接管者。

**责任边界：问责永远无法对 Agent 成立，残余责任永远由人承担。** Agent 不能赔钱、不能坐牢、不在乎声誉——问责这个条件在原理上就无法对它满足。无论机制建得多完善，每一个被委托的任务，都必须有一个有名有姓的人类 owner 对结果负责。"有名有姓"四个字不是修辞：出了事故，总要能找到一个人来回答"为什么当时信任它到这个程度"——这个问题，任何日志都替人回答不了。Mitchell 等人的立场论文把这条边界的论证推到了最强：让渡给 Agent 的控制越多，对人——尤其在安全上——的风险越大，所以自主性应当按任务风险分级，而不是默认追求全自动；完全自主、不预留人类接管的 Agent 系统，本身就不该被开发（[Fully Autonomous AI Agents Should Not be Developed, arXiv:2502.02649](https://arxiv.org/abs/2502.02649)）。

到这里，可以解开本文表面上的一个矛盾了。第二节说，人是缺失机制的"肉身替代品"，补位应当被资产化消灭；这一节又说，人永远要留在流程里。人到底该在还是不该在？

答案是：补位补的是**缺的机制**——验证、监督，这些能建成资产，建成之后人应当退出；裁决担的是**不可转移的责任**——问责，这个建不成资产，人必须留下。该资产化的补位全部资产化之后，人剩下的唯一角色就是裁决者：

> **人不是被挤出流程，而是被推到流程中唯一不可替代的位置。**

## 七、回到开头的问题

第一节的问题是：什么条件下，把结果责任交给 Agent 而不盯过程，是理性的？

现在可以回答了。当——意图被资产化地给定，而不是指望它"懂"；错误被定价和预算，而不是被假装不存在；自主链条被控制在可靠性半径之内；验证被前置成资产，而不是靠人肉复核兜底；授权沿阶梯逐级挣得，而不是第一天全量开放；并且，有一个有名有姓的人守在裁决的位置上——这时候，放心是理性的。注意这个答案里没有一项是"等模型再强一点"：六项条件，每一项都是今天就能动手的机制。

回头看，本文从头到尾没有回答"Agent 到底有多强"——那是别人的图表。本文只回答了一件事：委托从来不是能力的函数，而是机制的函数。能力决定天花板在哪，机制决定你敢把多少任务放到离天花板多近的地方。

所以，"如何放心地让 Agent 开展工作"的最终答案是：**放心不是一种感觉，也不能靠等待下一代模型批发得来。它是一套机制运转的副产品。** 机制到位的团队，今天就可以放心；机制缺位的团队，再强的模型来了，也还是"Agent 做一遍，人再做一遍"。

模型的能力曲线会继续涨，这不由任何人决定。但委托时代的到来速度，取决于有多少人开始动手建机制。
